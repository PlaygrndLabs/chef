# site

The hosted chef at chef.playgrndlabs.com (also `chef-site.<subdomain>.workers.dev`): the landing page and the chef app on one site. The app's UI and sign-in live here; each person's chef engine (agents, sandboxes, repositories, keys and previews) runs in their own Cloudflare account.

1. `/auth/start` sends a visitor to Cloudflare's consent page; `/auth/callback` trades the code for a short-lived token and reads their Cloudflare user. The `Members` directory maps that Cloudflare identity to a chef user (`usr_…`) and, on first sign-in, creates a default organization (`org_…`, named after them) with them as its owner, the way Cloudflare gives every sign-up an account and ChatGPT and Claude give every person a personal workspace. The signed session cookie holds the user and the organization they are working in.
2. Everything people build belongs to an organization. Each `Organization` Durable Object holds its name, its members with their role (owner, admin or member) and its engine: address, Cloudflare account and the key this site uses to reach it. Owners and admins set chef up and rename the organization; members use it. A person can create more organizations and switch between them from Settings.
3. `/setup` lists the person's Cloudflare accounts. Setting up runs `installer/install.mjs` in their `Member` container (one per person, holding their short-lived Cloudflare token and setup progress): it copies the prebuilt sandbox image into the account's registry, creates a token limited to Workers scripts for previews, and runs `chef deploy --image` with a generated `CHEF_PASSWORD` that only this site knows and `CHEF_SITE` set to `SITE_URL`, so the engine has no dashboard or sign-in of its own and sends anyone who opens it directly to this site. Each organization's engine gets its own Worker name, such as `chef-acme-x7k2`, so one Cloudflare account can run a separate chef for every organization its owner makes; the engine's repos, memory, workflows, previews and live apps all carry that name. The finished engine is stored on the organization.
4. Signed-in people get the dashboard at `/`, and `/api`, `/agents` and `/preview` are proxied to their current organization's engine with that key, after checking they are still a member. The engine sends GitHub back to this site through the `x-chef-origin` header.
5. The `Members` directory also lists every person and organization and how each setup went. People who can see the PlaygrndLabs account itself (the account in `CF_ACCOUNT_ID`) when they sign in are admins and see that list at `/admin`.
6. The Cloudflare token is revoked as soon as setup ends. When a newer engine is out, the dashboard asks an owner or admin right after they sign in: Update now or Later (asked again at the next sign-in). While an update runs the site answers the engine's API with 423 for everyone in the organization (the dashboard shows the progress and locks projects and chef's settings), while account, organization and members stay open. The lock lifts when the update ends, or after 30 minutes.
7. Owners remove chef at `/remove`. For an organization this deletes it; Personal can't be deleted (chef doesn't delete accounts), so there it uninstalls chef and leaves Personal ready for a new setup. Since the site keeps no Cloudflare access, the owner signs in once more (`/auth/start?then=remove`, which keeps that token until the removal ends). The `Member` object then runs `src/uninstall.ts` against the account: it lists what the organization's engine made and removes exactly that, by name and tag. That is the engine Worker (refused if a Worker by that name isn't a chef engine), its event triggers and workflow, the container applications bound to its Durable Objects, every Worker tagged `chef-project` named `<engine>-<project>` (but not those of another engine whose name starts the same way), the Artifacts repos in the engine's namespace, its `<engine>-memory` index, the `chef previews (<engine>)` token and the sandbox image when no other chef on the account uses it. It checks the account again afterwards, and only then forgets the organization: its engine, members, invitations and sharing. If anything fails, the organization stays and signing in again picks up where it stopped. The `uninstall` workflow checks this on the PlaygrndLabs account with a throwaway engine set up by the real installer.

The `site` workflow publishes the sandbox image, deploys this Worker after every green CI on `main`, attaches chef.playgrndlabs.com when that zone is in the same account, creates the OAuth client once (scopes in `oauth-scopes.json`), and on later runs keeps its name, logo and home page current. Cloudflare keeps its own copy of the logo, so `logo_uri` carries the hash of `public/logo.png` and changes with it. It uses `SITE_CLOUDFLARE_API_TOKEN` and `SITE_CLOUDFLARE_ACCOUNT_ID` when set, so the site can live in the account that owns the domain, and the organization's Cloudflare secrets otherwise. The client is private until a verified domain makes it public.
