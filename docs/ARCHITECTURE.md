# Architecture

Chef turns a prompt or a spec entry into a merged feature on its own. The spec is the memory, git is the state, and chat is only input.

## Where things run

Chef runs on Cloudflare, in the person's own account.

The engine is the Chef Worker in that account: the HTTP API, the project and session Durable Objects, sandboxes (each branch's development environment, where its whole app runs), Artifacts repos, memory and settings. Everything that does work or keeps state lives there, so work goes on when no client is open. The engine serves the dashboard itself, behind its password, which signs in from a browser only. Programs use API keys (`chef_<id>_<secret>`, kept as a hash in the `Settings` Durable Object, each named, with an optional end and its own revoke; `workers/src/grants.ts`). Every key carries a list of scopes, all full access for now, so narrower keys and share links are new scopes rather than a new mechanism. An engine can be run for people by a separate app: that app holds a controller key, usually the deployment's `CHEF_API_KEY` from `chef deploy --api-key`, and only a controller's requests may name the person they act for (`x-chef-user`) and the address their links use (`x-chef-origin`). An engine with a key and no password has no sign-in or setup page, and sends a browser that opens it to `CHEF_HOME` when that is set. Several such apps can drive one engine, each with its own key. A share link is the same kind of grant (`share`, `workers/src/shares.ts`) with narrow scopes: `session:<project>/<id>` reads that session, its commits and its changes, and `app:<project>/<id>` opens the running app of that session, or of `main`. The Worker turns a request into the scope it needs (`scopeFor`) and refuses everything else, so a link can never write, list or reach another project. The link itself is `<origin>/s#<key>`: the key stays in the fragment, which browsers never send, and the read-only page at `/s` (`apps/dashboard/src/components/shared-page.tsx`) sends it as a Bearer token. An app opened through a share link remembers its visitor for one hour instead of twelve, so ending a link shuts it out within the hour, or at once with a new app key. Who may open a link is up to whoever serves it: a Chef on its own gives it to anyone who has it, and an app that runs Chef for others can check people before it passes the request on. That app can swap in its own share dialog through the dashboard's `Host.Share`, or hide sharing with `Share: false`. A terminal or desktop app would be another client of the same API.

Every deploy goes through `chef deploy` (`pnpm run deploy`, `cli/src/deploy.ts`), from a terminal, the Deploy to Cloudflare button or the `deploy` workflow. It reads the root `wrangler.jsonc`, creates the Vectorize index when it is missing, and runs `wrangler deploy`. With `--name`, it writes a copy of the config where the Artifacts namespace, Workflow, memory index, transcript bucket and app router carry that name, so several chefs can share an account. A name is `chef` or starts with `chef-`, so everything Chef makes on Cloudflare starts with `chef` (see [Names on Cloudflare](SELF_HOSTING.md#names-on-cloudflare)).

## Packages

| Package | Role |
| --- | --- |
| `core` | Spec format and lint, router, session state machine, orchestrator, merge, ports and their in-memory fakes, code rules. No I/O. |
| `adapters` | Real implementations of the ports: Artifacts over isomorphic-git, Jev classifier, Claude planner and reviewer, and `ChefAgent`, the AG-UI agent CopilotKit streams sessions through. |
| `workers` | The engine, the Chef Worker: `ProjectAgent` and `SessionAgent` Durable Objects, the coder sandbox, the `chef-upstream-sync` Workflow, the HTTP API. |
| `template` | The vertical-slice template every project Chef builds starts from, with its own `app` CLI (`gen`, `drive`, `proof`). |
| `cli` | `chef` CLI: spec lint, code rules, routing, `chef deploy`, the local demo with real checks, benchmarks, the Jev spike, and `chef serve` (the dashboard on the in-memory world, used by the browser tests). |
| `apps/dashboard` | Dashboard served by the Chef Worker (React, built with Vite into `dist/`): the feature list on the left (main on top, which opens a main tab with main's running app, the release candidate, and a History of `main`: its commits, each commit's files and their diffs, like a desktop git client; child features under their parent, working ones first; rename, move and delete in place), the features opened as tabs in the middle after main's own tab, which always comes first, cannot be closed and shows whenever no feature is picked (on a phone the chat shows instead), each feature opening on its running app with its messages, changes (the session's own branch: its commits and their diffs, and all its changes against where it branched off), checks and details one click away, and on the right the CopilotKit chat, the only place a person asks for work. A site that runs engines for others can build the same dashboard with its own `src/host/` folder, which adds account, menu and settings parts through the `Host` interface in `src/lib/host.ts`; Chef's own `src/host/` adds nothing. |
| `agents` | Specialist profiles with write scopes. |

The Chef logo has one source, `core/src/brand/brand.ts`. The dashboard and the engine draw it from there, and `core/src/brand/files.ts` turns it into the logo files other places need: the light and dark wordmark SVGs, the favicon and the mark as a PNG on white at 256 and 1024 pixels. `node cli/src/brand.ts <folder>` writes them, with only Node and no install, so the README's `docs/assets` and any site that shows Chef's logo build them from the same source; a unit test fails when `docs/assets` drifts.

| `CheckRunner`, `ProofRunner` | `FakeCheckRunner`, `FakeProofRunner` | `LocalCheckRunner` and `LocalProofRunner` (`cli/src/local`), `SandboxCheckRunner` and `SandboxProofRunner` (`workers/src/sandbox-checks.ts`) |

| `MemoryIndex` | `LexicalIndex` (TF-IDF) | `VectorizeIndex` (`adapters/src/vectorize.ts`, Vectorize plus Workers AI `@cf/baai/bge-base-en-v1.5`) |
| `EventBus`, `KeyValueStore`, `Clock`, `IdSource` | memory versions | `DurableEventBus`, `DurableStore` in `workers/src` |

The planner and reviewer call Claude through `adapters/src/anthropic.ts` with structured output validated by zod. The model provider is the user's choice, like in any other app: an Anthropic API key, or a custom Anthropic-compatible provider with its base URL and key. `adapters/src/settings.ts` resolves it with the rest of the app's settings (Cloudflare account for app addresses, TypeSafe key, model ids, attempts, voice): settings saved in the dashboard (`/api/settings`, kept in the `Settings` Durable Object) win over the Worker's secrets. An app that manages the engine with a controller key can take over the three providers (Claude, Jev and voice) with `PUT /api/settings/managed`: from then on the engine uses only those, ignores saved and deployment keys for them, and refuses to save its own. Every service Chef pays for is one entry in `PARTS` (`core/src/usage/budget.ts`): an id, a label and a group (`models` or `cloudflare`) that decides its column in the usage tables. Spend is always a `Spend` (micros by part); totals are sums of it, never stored. The `Settings` object keeps one record per month (`spend/month/<YYYY-MM>`, `MonthSpend`: each project's and each person's `Spend`), so past months stay, and `GET /api/usage` answers it as a `Ledger` (org, project and person totals for budgets, plus the parts), for any `?month=`. Adding a service is a line in `PARTS` and a call that records its cost; the budgets, the ledger, each build's cost and every usage view pick it up. Every model call is metered by part (`model`, `router`, `voice`), from the tokens each answer reports at list prices: Claude's `usage`, Jev's `usage`, and the Realtime `response.done` or GPT Live session usage. Sandboxes are metered too, as part `sandbox`: each `SessionAgent` keeps its running container's start (`sandbox/run`) and counts Cloudflare's list price for its size's memory and disk for every second it is up, plus the CPU seconds it was busy (read from `/proc/stat`), whenever it checks for idleness, is asked its status and stops (a run cut off without notice is closed on the next start, at its last use plus the idle time). It reports each stretch to `ProjectAgent.sandboxSpent`, which records it for the person who asked for the build (none for main) and adds it to the build's own cost (`project/spend/<session>`, a `BuildCost`: the build's `Spend` per month, with model calls made for that build). Calls that belong to no build (the project chat, live talk, routing, planning) go to `project/spend/project`, so a project's rows always add up to its month. Workers requests, Durable Objects and Artifacts are not metered; they mostly fit in the Workers Paid plan. Without a TypeSafe key the router skips Jev (`NO_CLASSIFIER`) and the planner triages every request that rules do not settle. Only the direct Anthropic API path opts into server-side model fallbacks; a custom provider gets plain requests without beta headers.

## Flow of one prompt

1. **Route** (`core/src/router/router.ts`). Rules first (`/new`, `@feature` mentions, English questions). Then Jev answers three typed choice questions (intent, feature, change kind); its answer is used only above per-action confidence thresholds. Otherwise the planner triages.
2. **Split** (`Router.split`). For a new feature or a change the router did not settle by rules, the planner splits the request into independent parts, one session each, built in parallel. A part that adds a capability is a new feature. It names an existing feature as its `parent` (spec field) only when using it takes that feature's steps first, as in `PATH.md`; the planner then gives the steps that follow from the parent as the part's `path`, and `Router.split` drops a parent that comes without them, so another page of the same app stays a top-level feature. A part with a parent sits under it in the dashboard's feature list and may also change that parent's folder. A fix or refactor of one feature stays a new build of that feature. `#feature`, `/new`, `/chore` and `/hotfix` requests are never split.
3. **Plan**. The planner returns the feature spec and work items. A chore gets no plan from the model: its title is the first clause of the request, cut at a word, and its id is `chore-` plus up to four of its words (`choreTitle`, `choreId` in `core/src/ports/planner.ts`), so "Dockerize the project" becomes `chore-dockerize`. The Dockerize suggestion sends just that request with `/chore` (`COMPOSE_PROMPT` in `core/src/app/compose.ts`), so it always runs as a chore whatever the router would say. What a compose file must hold for Chef to run it (every service, the dev web page on a published port, a Dockerfile for each `build:` service, healthchecks with `depends_on: condition: service_healthy`) is not in the request: it is `COMPOSE_GUIDANCE`, part of the project structure guidance every planner, builder and reviewer gets, so it also applies when a person asks in their own words or a feature adds a service. Existing acceptance criteria are never dropped, and a spec change is always the first item.
4. **Session**. The orchestrator forks canonical `main` into `<project>--<feature>--<session>` and drives the state machine in `core/src/session/machine.ts`:
   `queued → planning → testing → coding → reviewing → gating → merged | stuck | dropped`.
   A prompt can start several attempts. Each attempt is its own session with its own fork, sandbox and running app until it wins.
5. **Turns**. Each coder turn runs one work item under one profile. Its changed files become one commit on the fork with a note under `refs/notes/chef` (prompt, root prompt, run id, model, role, spec revision, paths). Installed dependency folders (`node_modules`, `.pnpm-store`, `.yarn/cache`, `__pycache__`, `.venv`) are never part of a turn's changes, even in a repository that does not ignore them. A turn is rejected before it is committed, and the reason fed back, when it writes outside its role's scope, when a non-test role changes a test the test role wrote (locked tests), when a test turn on a Chef template project adds tests that pass against an empty stub of the feature (red check, using per-test results from node's TAP output), or when it breaks a project lint rule in `lint/rules/` (project-lint). Most of these are also caught while the turn runs, so the agent fixes them in the same conversation instead of losing the turn: the orchestrator sends the runner a `TurnGuard` (the role's scope as regexes, generated files, locked tests, files other lanes own, and the learned rules), the runner's `PreToolUse` hook refuses a Write, Edit or NotebookEdit to a path the turn may not change and says why, and after the turn the runner hands lint problems in the changed files back for up to two rounds: the template lint, which includes the learned rules, on a Chef template project, and the learned rules alone on a project with its own structure. A shell command can still write anywhere, so the checks after the turn stay. Before each turn the orchestrator recalls up to three memory documents, lessons and feature memories of the same feature first, and appends them to the prompt. Each profile runs in the Claude Agent SDK as a subagent named `chef-<role>`; the profile model `coder-default` resolves to `CODER_MODEL`. A role's effort (low to max, set next to its model in the agent settings, empty for the default) goes to the SDK as `effort`, and replaces the planner's and reviewer's own per-call defaults (low or medium for the planner's small calls, high otherwise). Every turn, and the planner and reviewer, also get the project's guidance (see [Memory](#memory)).
   When a plan has build steps for two or more plannable roles, the roles work in lanes (`Orchestrator.laneRound`, `core/src/session/lanes.ts`): each role has a `lane/<role>` branch in the session's fork and works in its own folder of the session's sandbox (`/workspace/<session>--<role>`), so the roles share one container; the sandbox keeps one turn per lane (`sandbox/turn/<role>`), with its files under `/workspace/turns/<role>`, so starting a lane's turn stops only that lane's earlier runner. Each round resets the lanes to the fork's head, runs one turn per lane in parallel, commits on each lane and merges the lanes back; lines two roles both changed go to the conflict-resolver. On a Chef template project Chef first commits one part file per role in the feature's folder (`laneLayout`). Tests are written before the lanes start, and chores never use lanes.
6. **Running app**. Each session's sandbox is the development environment of its branch: the coder's files and commands, and the project's whole stack. After each commit, `Orchestrator.runApp` asks the `AppHost` to run that commit in the background, so the session moves on to its next step without waiting; the gate's proof waits for the app of the head it checks, and gardener commits start no app. In the sandbox, a newer commit waits for the run in progress and replaces it, and a run nobody wants any more is skipped. `workers/sandbox/app.mjs` updates its own copy of the branch (`/workspace/<session>/app`, apart from the coder's working copy, which an app start never touches), and runs it one of two ways. A Cloudflare Workers project, which has a wrangler config at the root (`wrangler.jsonc`, `wrangler.json` or `wrangler.toml`) and no compose file, runs with `wrangler dev` on port 8787 and no Docker: the script links the sandbox's preinstalled template packages (`/opt/chef/template/node_modules`) when the project asks for exactly those versions and runs `npm install` otherwise, writes the project's keys to `.dev.vars`, and starts `wrangler dev` detached, logging to `/workspace/<session>/app.log`; the next start stops it first. Chef's template is such a project, so its apps start in seconds. Any other stack runs from the compose file at the root (`compose.yaml`, `compose.yml`, `docker-compose.yaml` or `docker-compose.yml`): the script builds every service that has a `build` and starts the stack with `docker compose up` on the sandbox's own Docker. The app's port is the `chef.port` label of a service, or the first published port. While it waits for that port to answer, the script watches the stack every two seconds and reports `failed` at once, with the tail of the logs of the service at fault, when a service exits with an error, keeps restarting, the app's own service stops, or a service logs a build error (`[ERROR]`, `Build failed`, `Failed to compile`) and still does not answer ten seconds later. A start has ten minutes in all (`APP_START_SECONDS`), and the port four of them; past that it fails with the stack's logs. `SessionAgent` stops a runner that has not reported by then plus a minute and fails the start with the compose logs, `SandboxAppHost` gives up on a sandbox that does not answer three minutes after that, and a `starting` state nobody follows any more (the object was reset mid-start) reads as asleep, so the next visit starts it again. People and the gate reach it at an address through Chef's router (see [Running apps](#running-apps)); proofs reach it on `127.0.0.1` inside the same sandbox. A branch with neither a wrangler config nor a compose file has no running app (`no-stack`), and its proof says so. Before a session moves to review, and again when a review step starts, the orchestrator waits for the app of the head commit (`appAtHead`, bounded by the same limits); if it `failed`, the session goes back to coding with `app_failed` and the app's log as the feedback (with lanes, to the roles whose files the log names), and the reviewer does not run. This counts as an attempt, so a branch whose app never starts ends `stuck` with "the app still does not start". `no-stack` never blocks. Nothing of the app is deployed to Cloudflare: where it runs in production is the person's choice, from their own repository.
7. **Review**. The reviewer compares the diff from the session's base to its head against the spec. It answers with a verdict for every acceptance criterion (`met`, `missing` or `unsure`) and the evidence behind it, the file and function and the test that covers it or what is absent; a `missing` criterion asks for changes even when the reviewer approved, while `unsure` only shows. The verdicts go out on `review.verdict` and the Checks tab lists them under the review. When every live attempt of a prompt has reached the gate, each attempt's code runs against the tests of all attempts and the reviewer picks one; the others are `dropped`.
8. **Gate** (`Orchestrator.gate`). Sync from `main`, then the project's checks (see [Project structure](#project-structure): the template's typecheck, lint with no comments and import boundaries, tests and generated files, or the repository's own install and scripts), spec lint, write scope of every commit by the role in its note, no coder commit touching a locked test, a reviewer approval from a model that wrote no code in the session of the current head, and a proof, stored under `refs/notes/chef-proof`: on a Chef template project the feature's flow driven against the branch's running app, on any other project a request to the running app at the feature's entrypoint page, or `/`, that must answer. On a Chef template project whose session changed only files inside `features/<id>/` folders (spec, `.chef/`, Markdown and generated files aside), the test check runs only those features' tests and the tests outside `features/` (`changedFeatures`, passed to the check runner as `features`, which narrows the test command's globs); a chore or a session that changed anything else runs every feature's tests on the synced tree. Every feature's tests still run on `main` after the merge (see below), and a failure there reverts it. On a Chef template project the proof also drives the flows of up to six merged features again on the same app (`proveMerged`, as a chore's proof does), so a feature that breaks an earlier one in the running app, through a route clash or shared storage, goes back to coding with that failure instead of merging. Merges run one at a time through a mutex, which holds only the merge itself. If `main` moved while the session was gated, it merges at once when none of the files `main` changed since its base are files it changed (generated files aside), and otherwise syncs and is gated again.
9. **Merge**. A gardener commit sets the feature's status to `merged`, adds spec entries for feature folders that have none (Chef template projects), condenses the session into `memory/features/<id>.md`, and writes any lint rule mined from corrections. Then `MainWriter.mergeFork` merges the fork into `main`. Only the gate holds `MainWriter`.

**Build steps.** Planning (2, 3), writing tests first (the test item in 3 and the testing state in 4) and review (7) are each a project setting (`steps` in Project settings > General > Build steps, `ProjectConfig.steps`), and all three are off by default, so a build takes the least time and the fewest tokens. With planning off there is no split and no planner call: `Orchestrator.directPlan` gives a new feature an id and title from the request's first clause (as a chore's, with a leading verb such as make or add left out of the id), the request as its one criterion and body, `GET /<id>` as its entrypoint on a Chef template project (`/` on any other), and one work item for the `backend` builder with the request as its prompt; a change to an existing feature keeps that feature's spec and gets one item. With tests off the test item is dropped from any plan, and a Chef template feature with no `flow.ts` is proved by asking the running app for its entrypoint and driving the flows of merged features again (`flowlessProof`). With review off the session still waits for its app at the head, then records an approval marked as skipped, which the gate's review check accepts. Whatever is off, typecheck, lint, the project's existing tests, the running app and main's checks after the merge still gate every change. The core treats a project without the setting as having all three on.

With tests on, the engine writes them alongside the code (`Specialization.testsAlongside`, on in the Worker): the test item becomes its own lane next to the builders' lanes instead of a testing state before them, and it still has to fail without an implementation. Once the lanes merge and the app starts, the session runs the project's checks at once (`quickChecks`, in parallel with the app start); new failures send the builders back with the log before any review, and the gate reuses those results when the head has not changed since.

A prompt routed as a question starts no session: it is answered from the memory index, by the planner when it has an `answer` method, and the answer lists the files it used.

When splitting, planning or creating the sessions fails after `route.decided` (a model error, say), `submit` emits `route.failed` with the reason and records it as Chef's reply in the chat memory, so the chat says that nothing is being built for that ask instead of showing it as started.

A failed gate, a rejected review or an app that does not start sends the session back to coding with the failure log. There is no cap on time or tokens: inside a turn the coder compacts its own context when it fills, and loops are caught by repetition instead. Every failure gets a fingerprint (`failureFingerprint` in `core/src/session/machine.ts`: the gate's failing checks and test names, else the failure text without timings, hashes and line numbers). When a failure comes back, the next turn is told it is the same failure and to change its approach; the third time, the session turns `stuck`. Roles that clash on the same lines count the same way, though a clash costs no try; conflicts from merging a moving `main` do not count. Four tries is the last backstop. A stuck session blocks no other session. Its page in the dashboard says why it stopped and shows what failed last (the session's `machine.feedback`, else the last entry of its `history`, else the reviewer's reasons).

### Work that outlives a deploy

`ProjectAgent.drive` runs in a Durable Object alarm every second while any session can move. It does not wait for the sessions: `SessionPump` (`core/src/orchestrator/pump.ts`) starts one step for each session that has none running and lets it finish in the background under `keepAliveWhile`, so a long gate or a followed coder turn in one session never holds back another, and a new session starts at once. Every state change bumps the session record's `revision`, and `Orchestrator.save` drops a save from a copy older than a stored merged, stuck or dropped record, so a write that read the session before it ended (a sync mark after a push to `main`, a step still running on an orchestrator that was rebuilt) never puts it back to an earlier state. A deploy resets the object, and an alarm may run for at most fifteen minutes, while one coder turn often takes longer. So a coder turn does not run inside the call that starts it. Before it starts, the orchestrator saves the turn's id in the session record (`turns`, one per lane), and `SessionAgent` launches the runner as a detached process in the sandbox. The runner writes its events and result to files next to it. The alarm then follows the turn for a minute at a time (`FOLLOW_SECONDS`), passing on new events. When the minute is up and the turn is still running, the step ends with `TurnRunning` and `drive` comes back a second later. A sandbox that gives no answer about a turn for six minutes (`TURN_ANSWER_MS`) is reset and the step is retried, so one wedged sandbox never holds a session forever. When other lanes still have turns running in it, the reset stops only that lane's turn and the container restarts once they have finished (`restartIfIdle`, or after five minutes when a stuck check still counts as running; an interrupted check simply runs again); a sandbox that cannot answer whether its other turns run is restarted at once. A person can do the same from a running sandbox's Restart button in the build's Cloudflare section (`POST /sessions/<id>/sandbox`): it waits for running turns the same way, and its notice offers Restart now, which restarts at once; those turns then continue where they stopped, from their saved conversation and file changes when the engine keeps transcripts. A step that starts after a deploy, a reset or an alarm timeout finds the saved turn and follows the same process from the last event it passed on, or takes its result when it has finished. The work is not started again. If the sandbox itself was replaced, that turn starts over with a notice in its activity, continuing its saved Claude conversation and file changes when the engine keeps transcripts (see below). The session becomes `stuck` with the reason when this happens three times, or when a turn runs past ninety minutes, so a session never waits silently. Checks, app starts and model calls are short and simply run again when a reset interrupts them. Scheduled work that can take minutes (starting main's app or a woken app, reading a project) is handed off with `keepAliveWhile` and returns at once, because the alarm runs its due jobs one after another and a long one would hold back `drive` for every session.

Each coder turn's full Claude transcript (every message, thinking block, tool call and tool result, and those of its subagents, as the Claude Agent SDK writes them under the lane's `claude/projects/`) is kept in R2, in the engine's own `<engine>-transcripts` bucket (binding `TRANSCRIPTS`). `chef deploy` finds or creates the bucket (`ensureTranscripts`), and nothing in it expires: a transcript stays until its project is deleted; when the token cannot use R2 the engine deploys without the binding and keeps no transcripts. The sandbox holds no key for it: the runner sends each changed file every fifteen seconds, so a restart loses little, and once more when the turn ends or fails, with `PUT http://198.18.0.2/<sandbox>/<path>` (`TRANSCRIPT_ADDRESS`), which `SandboxOutbound` stores as `<project>/<sandbox>/<path>` (`transcriptFetch`), so a sandbox can read and write only under its own project. The runner also saves `turns/<turn>.json` with the role, model, Claude session ids, the transcript's path, start and end time and outcome, and `turns/<turn>.patch` with its uncommitted file changes against the turn's commit (a `git diff --binary` built in a separate index, so the coder's own index is untouched). Deleting a project removes its transcripts.

A role keeps its Claude conversation across turns. The orchestrator remembers each role's last turn in the session record (`conversations`, keyed by lane and role) and passes it to the next turn of that role as `resume`. When a turn starts over because its sandbox was replaced, `resume` names the lost turn with `changes`: the runner restores that turn's transcript (from the sandbox, or from R2 when the sandbox is new), applies its saved patch to the fresh checkout and resumes the same Claude session, telling the agent the sandbox restarted and whether its file changes came back. When the same role works on the feature again (after a rejected review, a failed gate or a rejected write), the runner resumes that role's earlier conversation with the new task, telling it the repository has moved on. A conversation that cannot be found or resumed falls back to a new one, so a missing transcript never fails a turn.

A deploy does not switch every object at the same moment. A busy `ProjectAgent` can keep serving the previous version for minutes while its `SessionAgent`s already run the new one, so the two must understand each other across one deploy: a call between Durable Objects only ever gains new methods or optional fields, and an existing method keeps its arguments and its result's shape.

## Isolation

- Artifacts tokens are per repo, so each session has its own fork. The orchestrator holds the fork's write token; the coder receives a read token only.
- The coder runs in a Cloudflare Sandbox whose only network path is `SandboxOutbound`: it adds the read token for Artifacts, swaps a placeholder for the provider's API key on the provider's host, blocks `git-receive-pack`, and refuses other hosts. A sandbox registers that handler once each time its container starts, and the handler asks the sandbox's `SessionAgent` for the newest read token of the jobs running there and the provider's host and key, which jobs without a model (app starts, check runs) never clear (`outboundAccess`), so an app start, a check run and a coder turn that begin at the same moment never swap the handler under each other's git requests. The sandbox returns changed files as data; it never commits or pushes.
- Capabilities are separate objects (`core/src/orchestrator/capabilities.ts`): `Archiver` can only push `archive/*`, `MainWriter` can only merge or revert `main`.

## Environment and secrets

Apps Chef builds often need keys for outside services (payments, maps, email) or plain settings like an API base URL. Values shared by every project live under Settings > Environment (`GET`/`PUT /api/env`, kept in the `Settings` object); each project keeps its own set under Project settings > Environment (`GET`/`PUT /api/projects/:name/env`, `adapters/src/project-env.ts`). A project gets the shared values plus its own, and its own value wins for a name both have (`mergeEnv`); its view marks each variable as shared, its own, or its own over a shared one. Saving a shared value tells every project, so waiting sessions resume and running apps restart with it.

- **Storage.** `ProjectAgent` stores each value sealed with AES-GCM under a key the `Settings` object creates once per deployment. A secret is never returned again; a plain value is shown. Nothing goes into git or Artifacts.
- **Agents see names only.** The planner gets the names already set and lists the ones a feature reads in its spec entry (`env:` in the frontmatter, validated by `ENV_NAME` in `core/src/env/env.ts`). Each coder turn's prompt lists the project's names, the feature's names, and which are still missing. The app reads them from `context.env`; tests pass fake values to `testApp(t, features, env)`.
- **Running apps get values.** When Chef starts a branch's app, the engine writes the values into `app.env` in that sandbox (mode 600, outside the code) and adds it as an `env_file` of every compose service; a Workers project gets the same values in `.dev.vars` (mode 600, ignored by git), which `wrangler dev` hands to the Worker as `env`. The coder runs in the same sandbox, so a value a running app holds is reachable from that sandbox; the coder's prompt still gets names only. Saving a change restarts main's app and every session app that is running.
- **Needs a key.** A session whose feature lists a name that is not set stops before its gate, records `needs` and emits `session.needs`; the proof would only fail without it. It no longer counts as runnable, so `drive` stops rescheduling it. The dashboard shows it under "Needs you" with a field per missing key on the feature page. Saving a value calls `Orchestrator.environmentChanged`, which resumes every session that now has what it needs.

## Running apps

Chef owns the development environment only. Each branch has its own running app in its own sandbox, and `main` has one too, as the release candidate. Production is not Chef's: the person connects their own repository to wherever they run it.

- **Addresses.** One small Worker per Chef install, the app router `<engine>-app` (`workers/src/app-router.ts`, tagged `chef-router`), gives each running app an address: a Preview URL of the router per branch, `<session>-<project>-<engine>-app.<subdomain>.workers.dev`, and `main-<project>-…` for main. Each deployment of the router is the same small module (`routerModule`, `adapters/src/app-gate.ts`) with three bindings: the engine's `SessionAgent` namespace, the sandbox to reach (`CHEF_TARGET`) and the project's app key (`CHEF_APP_KEY`). It forwards every request to that sandbox (`SessionAgent.fetch` with `x-chef-app`), which proxies it to the app's port in the container. The user's app itself never runs on Workers. Chef makes an address the first time an app runs and keeps it until the project is deleted.
- **Private.** The router checks HMAC-signed passes with the project's app key, which only the engine holds. `/app/<project>/<id>` (a session id, or `main`) redirects to a link into the app, `/__chef/enter?t=…&to=<path>`, that works for two minutes and only on that address; the router trades it for a cookie on the app's own address (`__Host-chef_app`, HttpOnly, `SameSite=None; Partitioned`, so it also works inside the dashboard's frame) and passes nothing of Chef's to the app. Anyone else who opens an address gets a page that says to open it from Chef, so every link to an app the dashboard shows (the project bar's "Open main's app", the App tab's new-tab button, the app addresses in a build's Details) goes through `/app/<project>/<id>`, never to the bare address. `POST /api/projects/:name/app-key` makes a new key and redeploys every address, which ends every link and cookie at once.
- **Waking.** A sandbox that slept loses its running app. A visit to `/app/<project>/<id>`, or to the address itself, shows a page that refreshes while Chef starts the app again from the branch's latest commit (`ProjectAgent.wakeApp`); a merged session's link opens main's app.
- **Main.** Whenever `main` moves, `ProjectAgent.runMainApp` runs it in the `<project>--main` sandbox. The state (`starting`, `running`, `failed`, `no-stack`) is stored, sent as a `main-app.updated` event, returned with `/spec`, and shown in the project bar; `POST /api/projects/:name/main-app` starts it again. A stored `starting` that no run of this object follows (it was reset mid-start) counts as behind, so the next `/spec` or `drive` starts it again.
- **New projects.** The template is a Cloudflare Workers project with no Dockerfile or compose file, so its apps run with `wrangler dev`. An imported Workers repository runs the same way; any other imported repository has no running app until a compose file is added ("Dockerize the project").

## Resources

Chef serves many projects from one Cloudflare account, so nothing stays up that nobody uses.

- **Sandboxes.** Each session has a `SessionAgent` container for its coder turns, checks and running app, and main has one named `<project>--main` for main's app; each is the container of its own Durable Object (`scheduling_policy: durable_object`), so there is no `max_instances` cap, only the account's concurrent memory, vCPU and disk limits. Cloudflare bills a container's memory for every second it is up and its CPU only while used, so a sandbox starts with 3 GiB on one vCPU and grows when it runs out (`workers/src/sandbox-size.ts`: 3 GiB/1 vCPU, 6 GiB/1, 8 GiB/2, 12 GiB/4). After each job it compares the kernel's `oom_kill` count in `/proc/vmstat` with the count at start, and also reads an exit for lack of memory; either way it takes the next size, saves it for itself and as the project's floor (`ProjectAgent.sandboxNeeds`), and restarts at once if it is idle. Every later sandbox of the project starts at that floor. The size shows in a build's Cloudflare details. A sandbox runs Docker (`workers/sandbox/boot.sh`: `dockerd` without iptables; every service uses the host network, with service names mapped to `127.0.0.1`) and has the internet; only the requests to Artifacts and the model provider go through Chef's outbound handler, which adds the read token and swaps the placeholder model key, so neither is ever in the sandbox. Base images from Docker Hub go through a small mirror in the sandbox (`workers/sandbox/mirror.mjs`, set as `dockerd`'s registry mirror): it asks Chef's image cache first, over plain HTTP to an address only the outbound handler answers (`workers/src/layer-cache.ts`), and pulls whatever is missing from Docker Hub itself, with the sandbox's own address, handing it to the cache on the way. Each layer is kept in its own `ImageLayers` Durable Object, chunked and checked against its digest, so the next sandbox of any project gets it from the engine; a manifest named by its digest is checked and shared too, while a tag's manifest is reused only within its project, for six hours, and also when Docker Hub limits pulls. Anything unused for 30 days is deleted. Images a project builds are not cached. A container stops at its idle time (`sleepIfIdle`), the later of two minutes after its last command (`SANDBOX_IDLE_SECONDS`) and, while an app runs, the project's `appIdleMinutes` (one minute by default, at least one) after its last visit (`sandbox/last-visit`, noted at most every 30 seconds). Cloudflare's own inactivity timeout stays at five minutes or more, only as a backstop. The orchestrator stops a session's container as soon as the session merges, gets stuck or is dropped (`Coder.release`). The next command or visit starts it again, and the app is built again from the latest commit. A visit to the app address of a merged build goes to the app it merged into (`ProjectAgent.movedApp`), through that app's entry link, instead of waking the build's own sandbox.
- **Forks.** A fork lives only while its session does. When a session merges, its commits and notes are already on `main`, so the fork is deleted. When a session is dropped, its head and notes are first pushed to `archive/<session>` on the canonical repo, then the fork is deleted. Turns and changes of an ended session are read from the canonical repo. If a merged feature is reverted later, the orchestrator forks `main` again under the same name and restores the session's work there. `Orchestrator.reclaim` releases sessions that ended before this cleanup existed, or whose cleanup failed (`fork.kept`).
- **Deleting a project.** `DELETE /api/projects/:name` with `{ confirm: name }` (Project settings > General > Delete project) removes only what Chef made for that project, in order: it marks the project as being deleted (alarms stop and every request to it, reads included, answers 409, so a page still open on it cannot restart main's app or read the code being removed), destroys the sandboxes of its sessions, lanes and main (`SessionAgent.discard`), deletes the addresses of its apps on the app router, removes its coders' transcripts and the memory entries it indexed (`Orchestrator.forgetMemory`), deletes its session forks and canonical repo, and destroys its `ProjectAgent` (settings, keys, chat, history). Then the `Settings` object drops it from the list, its budget, its GitHub link and its share links. A linked outside repository is never touched. If a step fails the project stays listed and deleting it again finishes the job.
- **Seeing them.** The Details tab of a session shows its cost so far (model and sandbox), its limits, and the resources only that build uses, one line each that opens to its ids, price and dashboard link (see `GET /api/projects/:name/sessions/:id/cloudflare`). Project settings > Usage shows the project's month (spent against its budget, by part, from the ledger's `projectParts`) and what each build, main's app and the project chat cost this month, in one column per group (`GET /api/projects/:name/usage`, `projectUsage`). App settings > Usage lists every project's month the same way, each opening that project's Usage. Durable Object namespace and container application ids are read once every ten minutes with the engine's Cloudflare token and left out when the token cannot read them.
- **Git in memory.** `ArtifactsRepoHost` reads through the Artifacts binding's read API (`log`, `readCommit`, `readTree`, `readBlob`) and keeps no git repository for reads; immutable commits and blobs sit in byte-bounded LRU caches. Only writes (commits, merges, ref and note pushes) use isomorphic-git, and they fetch just the refs they touch plus notes. At most three repos keep their in-memory git between operations, and one that grows past 48 MB is dropped and fetched again when next needed. Reads fall back to git smart HTTP when the binding has no read API.

## Merging and sync

- `threeWayMerge` in `core/src/git/tree.ts` merges trees line by line. Generated files such as the template's `src/registry.gen.ts` are never merged; resolvers regenerate them from the merged tree.
- A push to canonical `main` emits `cf.artifacts.repo.pushed`, which starts the `chef-upstream-sync` Workflow. It ignores forks and non-`main` refs and tells `ProjectAgent`, which marks every active session for sync. Sync runs between turns: a session that is mid-turn is synced when the turn ends.
- Branches follow the feature list from top to bottom: `main -> parent -> child`. A session whose feature's parent has exactly one open session branches from that session's head (`record.upstream`, `upstreamBase`; `Orchestrator.upstreamOf`), and waits in `queued` until the parent has a head; any other session branches from `main`. A child plans and writes its tests while the parent builds, but holds before coding (`session.held` naming the parent) until its branch has taken in the parent's feature (`features/<parent>/index.ts` on a Chef template project; on any other, until the parent has started its code), since using it takes the parent's steps first; so it codes against the parent's code, and files regenerated on its branch, such as the registry, list both. Before every step a session takes in its upstream's new commits (`followUpstream`: the same merge as a sync from `main`, conflicts go to the conflict-resolver). When it is done its gate merges it into the parent's branch instead of `main` (`gateInto`, a merge commit under the merge lock, only while the parent is between turns), emits `branch.merged` and counts as merged; the dashboard shows it as Done until the parent reaches `main`, and its app link opens the parent's app. When the upstream merges first the session moves to the next open ancestor or `main`; when it is stopped the child fails with a message, and while it is stuck the child waits.
- Merging is automatic by default. With the project setting `merge: "manual"`, a session whose checks pass stays in `gating` with `ready` set on its record and emits `session.ready`; it is not stepped again until someone calls `POST /api/projects/:name/sessions/:id/merge` (`Orchestrator.approveMerge`). Its gate then syncs from `main` once more, reuses the passing checks when nothing changed or runs them again when it did, and merges.
- Versions. A feature normally has one line of work. `POST /api/projects/:name/sessions/:id/version` (`Orchestrator.newVersion`, Try another version in the feature list) starts another session for the same feature with the same plan, its own fork and sandbox, and the person's note as a steer; the two get `version` 1 and 2 (`session.versioned`). While two or more versions of a feature are open, none merges on its own: each waits in `gating` with `ready` set, as with manual merging, and the one a person merges archives the others (dropped with "version N was merged instead"). The feature list shows each open version as its own row (v1, v2) with the sub-features that branched from it; when one is left it is a single row again. A sub-feature asked for while its parent has several open versions branches from `main`.
- A conflicting sync is still committed: the fork gets a two-parent merge commit with hunk-level conflict markers, and the session gets a conflict work item, using the conflict-resolver profile when one exists. Since both parents are recorded, later syncs and the gate do not recompute the same conflict.
- After every merge the checks run on `main`, outside the merge lock and after the session already counts as merged, as in a post-merge test pipeline. The gate records the merge as `verify/<commit>` in the project's store, and `Orchestrator.verifyMerges`, called from every `ProjectAgent.drive` (which keeps coming back every five seconds while one waits), runs them one at a time in merge order, in the background; a reset only means it runs again. A gate does not merge while one is waiting, so every merge lands on a `main` whose last merge was checked and failures are blamed on the right one. If they fail, the merge is reverted and the session reopens on its restored work with the failure log. A sandbox runs one check job at a time (`SessionAgent.runChecks`), since they share its checks folder. `revertMerge` does the same for a failure reported later: it undoes only that merge when later merges allow it, and otherwise returns `main` to before it and reopens every session merged since, without charging their attempt budgets.

## External git

The project's code always lives on Artifacts, and every session and gate works there. A project can be linked to an outside repository (GitHub first, any https git host for the branch mode) from the dashboard's "Project settings" dialog. The link is optional and only keeps the two in sync; unlinking leaves the project on Artifacts as it is.

- **Connect GitHub.** Like Vercel or Cloudflare's own Git integration, "Connect GitHub" sends the person to GitHub and back instead of asking for a token. Each Chef deployment owns its own GitHub App, created on first use through GitHub's [manifest flow](https://docs.github.com/en/apps/sharing-github-apps/registering-a-github-app-from-a-manifest): `GET /api/github/connect` posts a manifest (contents and pull requests write, push events, webhook and redirect URLs on this deployment) to GitHub for the person's account or an organization; GitHub calls back `GET /api/github/created` with a code that Chef trades for the app's id, private key and webhook secret, stored in the `Settings` object. Chef then sends the person to the app's install page, where they pick repositories, and GitHub returns them to `GET /api/github/installed`, which reopens the project's dialog. The dialog lists every repository the app's installations can reach; linking one stores the installation id instead of a token, and Chef mints a one-hour installation token (signed with the app's key, cached until five minutes before expiry) whenever it pulls, pushes or opens a pull request. Pushes reach Chef through the app's webhook, `POST /api/github/webhook`, which routes them to the projects linked to that repository. Other hosts, or a person who prefers it, still link with a URL and an access token. An outside dashboard that runs one shared GitHub App for many Chefs can instead hand Chef a broker (`PUT /api/github/broker` with `{ url, key }`, owner or controller key only). The app's private key then never reaches Chef: Chef asks `GET {url}` for the app and the installation ids it may use, and `POST {url}/token` (`{ installation }` → `{ token, expiresAt }`) for a one-hour installation token, both with the broker key as a bearer token. The broker receives the app's webhooks itself and reports pushes with `POST /api/github/pushed` (`{ repository, ref }`). While a broker is set, `GET /api/github` answers with `shared: true` and Connect GitHub goes to the broker's install page instead of the manifest flow.

- **First look.** Right after a project is imported from a repository, Chef reads the project the way a new teammate would (`adapters/src/project-explorer.ts`: the file list plus README, task lists, `package.json`, spec and top-level docs) and asks the planner model for a short summary, the open problems it can see evidence for, and three first tasks. The dashboard shows them as chef's first message in the project, with a button per task that sends its prompt. A fresh project from the starter app has nothing of its own to read, so it skips this and opens on the welcome screen.
- **Import.** When a linked project has no `main` yet, `bootstrap` takes the repository in instead of the template: through Artifacts' own import when it can, otherwise by copying the branch over git. Chef places no limits on its stack: a repository that does not follow the Chef template keeps its own layout, language, test tool and checks (see [Project structure](#project-structure)).
- **Inbound.** `ExternalSync.pull` (`core/src/sync/external.ts`) copies the repository's main branch to `external/<branch>` on the canonical repo and merges it into `main` like any other change, so running sessions sync with it as usual. A conflict does not block anything else: Chef forks `main` to `<project>--sync--<id>`, commits the merge with conflict markers, lets the conflict-resolver profile fix it, runs the checks, merges it into `main` and deletes the fork. If that fails, `external.stuck` is emitted and Chef waits for a new push to that branch or "Sync now". Chef checks the repository every five minutes and at once when GitHub calls `POST /api/projects/:name/git/webhook` with a push to that branch (signed with the project's webhook secret).
- **Outbound.** A per-project setting decides how work goes back. Chef never pushes to the repository's main branch, and a merged pull request comes back as an ordinary inbound change:
  - `off`: pull only.
  - `branch`: `main` is mirrored to the sync branch (`chef` by default) after each merge.
  - `pull-request` (the default): the sync branch, plus one pull request that Chef keeps up to date. It lists the features merged on Chef but not yet on the repository's main branch, with a link to main's running app.
  - `feature-pull-requests`: the sync branch, plus one branch (`<sync branch>-<feature>`) and pull request per merged feature. Each is the feature's own diff applied on the repository's main branch.
- **Access.** A link through Connect GitHub stores only the installation id. A link by URL takes a token that can push branches and open pull requests; it is stored in the project's Durable Object, and only its last four characters come back to the dashboard.

## Feature list

Features are first-class. Each project's feature list is a feature map kept in its repository under `.chef/features/` (`core/src/features`): one folder per feature named by its short name (unique in the project, the `featureId` sessions use), sub-features in sub-folders. A feature needs only a title; its session, branch, sandbox and running app may not exist.

- `SPECS.md`: frontmatter `title` and `state` (`current` when the code on that branch has it, `wish` when it is wanted and not built); the body may describe it.
- `PATH.md`: the steps from the parent feature's state to this feature's state. `.chef/features/PATH.md` says how to spin up the project. The whole way to a feature is the root file, then each ancestor's, then its own, so B sits under A when reaching B takes A's steps and more.
- "Map the current features" (a chat suggestion for every imported project without a map, the `/map` command, or a request like "map the existing features") makes the planner model explore `main` (`adapters/src/feature-mapper.ts`: the file list plus the README, manifests, routes, pages and other source, within a size budget) and return features with parents and paths. `placeMapped` puts each under its parent by short name, skips ones already listed, and Chef commits the new folders to `main` under the merge lock, so they reach a linked repository through the usual outbound sync. The first mapping also writes the root `PATH.md`; the suggestion shows while `.chef/features/` is empty. A project without `.chef/features` simply has an empty map.
- When a feature merges, the gardener makes sure it is in the map as `current` (`mergedEntryChanges`): a wish of the same short name turns current where it is, and a feature that is not listed yet gets a folder under its parent's, with `Open <entrypoint>.` as its path. So the first feature Chef builds starts the map.
- The dashboard's feature list shows every mapped feature, with or without a session, under its map parent, plus features that only have sessions or spec entries. Each row starts with a small pixel mark: a flag when the code has it, a lamp for a wish, a crane while a session builds it; with a session, the mark takes the session's state color. A feature without a session opens on its page: the whole way to reach it (start, each ancestor's steps, its own steps, which can be edited), its specs, and Build it for a wish or Ask for a change.
- People change the map from the feature list (`POST /api/projects/:name/feature-map` with an add, update, move, remove or start edit), each change one commit on `main`: Add a wish (at the top level or under a feature), rename, move and delete a mapped feature. Deleting a feature removes its map folder with its sub-features in the same commit; deleting a mapped feature that was never built only takes it off the list.
- The router sees mapped features alongside the spec, so `#<short name>` and plain requests reach them, and the planner gets the map outline when it splits, plans and answers. Its prompt (`agents/planner.md`) explains the map with Chef's own feature list as the example.

## Memory

The project repo is the memory; the index is a cache of it.

| Kind | Where | Written by |
| --- | --- | --- |
| Project memory | `memory/**/*.md` with `kind` and `feature` frontmatter, and the spec | the gardener and the gate, through commits on `main` |
| Notes | `memory/notes/<slug>.md` | a person, from Project settings > Memory, which also edits or removes any memory document |
| Lessons | `memory/lessons/<feature>-<commit>.md`: the failing checks, the acceptance criteria and the prompts behind a reverted merge | the revert commit itself |
| Feature memory | `memory/features/<id>.md`: one section per session (parent session, prompt, turns, corrections) | the gardener commit before each merge |
| Learned lint rules | `lint/rules/<id>.json` (`files` glob, `forbid` line regex, evidence) | the gardener, from corrections |
| Session memory | the session record (`history` of feedback, `parent`) and pending corrections, in the Durable Object's SQLite | the orchestrator |
| Episodic memory | commits and their notes under `refs/notes/chef` | every turn |

After bootstrap, every merge and every revert, `syncMemory` compares content hashes of the memory documents on `main` with the last indexed set and upserts or removes only what changed. Sessions on the same feature form a tree: a new session's `parent` is the previous live session of its feature.

A correction is a rejected or failed turn followed by the turn that was accepted. For red-test corrections the candidate lines are the bodies of the tests that passed against the stub; for others, the lines the accepted turn removed. Literals are generalized. A line becomes a rule when corrections from at least three sessions share it, no accepted turn and no file on `main` matches it, and no rule already forbids it. Turns rejected by a learned rule do not produce new rules. `checkTree` also enforces the rules, so the gate fails on any match.

Guidance is read from `main` at each turn (`core/src/guidance`, `adapters/src/guidance.ts`): the instructions shared by every project (Settings > Instructions, kept in the `Settings` object), the project's `GOAL.md` and `AGENTS.md` at the repo root (Project settings > Instructions, committed to `main` under the merge lock), with the project's text winning where they disagree. A `CLAUDE.md` at the repo root, which imported repositories often have, comes after them as the repository's notes for coding agents, unless it only repeats or points to `AGENTS.md`; coder turns do not load Claude Code project settings, so this is how it reaches them. The planner, every coder turn and the reviewer get it as one block.

The main chat keeps its own memory under `chat/turns` in the project's store: the recent messages plus a running summary of older ones, which the planner writes when the chat passes its token limit. Each feature keeps its own context in its session.

`verifyMain` adds a `feature-map` check after every merge on a Chef template project: every `features/<id>/index.ts` has a spec entry and every merged spec entry has its folder.

The Worker binds the index as `MEMORY` (index `chef-memory`, 768 dimensions, cosine) and Workers AI as `AI`. Each project's documents live in their own Vectorize namespace, named after the project, and kinds are filtered after the query, so the index needs no metadata indexes. `pnpm run deploy` creates the index when it is missing.

## Voice

The voice front end hands spoken requests to the same router as typed prompts; the voice model only listens and speaks. It speaks as Chef itself, in the first person, never as a go-between: its instructions carry the features, the main chat so far (`Orchestrator.voiceContext`) and the builds, so it knows what the typed chat knows.

1. The live button in the chat composer (next to Send) opens a WebSocket to the project's agent (`/agents/project/:name?voice=1`). The browser captures the microphone with an AudioWorklet, resamples it to 24 kHz 16-bit PCM and sends it as binary frames; it plays Chef's audio from the same socket and stops playback when the user starts speaking.
2. `ProjectAgent` starts a server-side voice session with `VoiceHost.start` and relays the audio both ways: GPT-Live (`wss://api.openai.com/v1/live/sessions`) with an OpenAI key, or a custom provider's Realtime WebSocket (`/realtime?model=gpt-realtime`, server VAD, input transcription and a `work_on_project` tool). Provider keys never leave the Worker. Browser WebRTC is not used, since the model gateway accepts Realtime voice only over WebSocket.
3. The voice model decides when the user asked for something: GPT-Live sends `session.delegation.created`, and the Realtime adapter turns a `work_on_project` tool call into the same event with the request attached. `VoiceDelegate` (`core/src/voice/delegate.ts`) takes that request (or the transcript up to the delegation point), calls `Orchestrator.submitSpoken`, which routes it like a typed prompt and emits `voice.request` (its `route.decided` carries `spoken: true`), and answers with `session.commentary.append`, which the model speaks in the user's language. A request still in progress when the call ends keeps running: `VoiceCall.hangUp` waits for it, and its answer is saved as Chef's turn in the chat instead of being spoken.
4. `SpokenTurns` (`core/src/voice/turns.ts`) joins the transcript deltas into turns, one per speaker, and `Orchestrator.recordSpoken` emits each as `voice.turn`. The chat shows those turns as spoken messages in the same conversation as typed ones, so they stay after the call and on other devices. A spoken request shows only the feature cards it started, since the turn already shows what was said. Once a call ends, its turns and cards fold into one "Live talk" row that opens on click, so a long call doesn't fill the chat.
5. While a call is live the composer is replaced by a panel with a pixel orb that follows the microphone and Chef's voice, a Mute button and an End button (or Esc). Ending stops the microphone and closes the socket; the agent then closes the provider session.

`chef voice --say "<request>"` runs the same path locally: scripted transcripts by default, or with `--live` the request is synthesized to speech (OpenAI text to speech, or the Realtime provider reading it aloud) and streamed as audio to the same server-side voice session.

## Streaming to the app

Sessions reach the app through CopilotKit. The Chef Worker hosts the CopilotKit runtime at `/api/projects/:name/copilotkit` (`workers/src/copilotkit.ts`) with one agent, `default`, a `ChefAgent` (`adapters/src/agui.ts`):

1. The dashboard's CopilotKit chat sends the user's message to the runtime, which runs `ChefAgent` and streams its AG-UI events back over SSE.
2. `ChefAgent` reads the project's event cursor, submits the prompt to `ProjectAgent`, answers with the route it took, and then follows the project's events from that cursor.
3. `SessionStream` maps each Chef event of the sessions the prompt started to AG-UI: coder text deltas become assistant messages, coder tool calls become tool calls, every state change is a step (`<session>:<state>`), and the running app, review, gate, merge and stuck results update a shared state snapshot (`ChefState`) that the chat renders as session cards.
4. The run ends with a summary line when every session has merged, got stuck or been dropped.

The dashboard follows a project's events over `WS /agents/project/:name`, and over `GET /events` every few seconds when the socket fails or has not opened within four seconds. It shows each part as soon as its own data is in instead of waiting for all of it: main's tab and its app need only `/spec`, the feature list and project bar `/spec` and the sessions, the chat the event history and the sessions, and Chef's first look at the project shows when `/overview` answers.

`chef serve` runs the same runtime and dashboard on a computer against the local world (fake coder, real or fake checks).

The start page shows what changed lately. Each `ProjectAgent` listens to its own events and keeps one line about the latest change people care about (work started, a feature merged into `main`, a feature waiting on a key, a change undone, commits pulled from the linked repository) in the `Settings` object (`noteProjectActivity`, `activityNote` in `adapters/src/projects.ts`). `GET /api/projects` returns it with each project as `updatedAt` and `note`. The dashboard's start page lists every project in the sidebar and shows the six most recent in the middle, by the later of that change and when this browser last opened the project.

## Learning

Every session leaves a labelled record: the change the reviewer approved, and what happened to it afterwards.

1. `review.verdict` events carry the reviewed head and base commits. `reviewPoints` (`core/src/learning/export.ts`) follows each approved review to its outcome: `gate-failed` when the merge gate failed, `reverted` when the merge was later reverted from main, and `merged` otherwise.
2. `exportOutcomes` turns each point into a reviewer example: the spec's acceptance criteria and the feature's files (`reviewMessages` in `core/src/learning/review-prompt.ts`), with `approve` as the target for merged changes and `reject: <why>` for the others. Each coder turn (its prompt and its changes, from the commit's note) is labelled positive or negative by the review it led to.
3. `chef tune data` runs the benchmark's 20 training features and 10 held-out features in separate projects with real checks and writes `tune/data/{train,heldout}.jsonl`, the coder turns, and each run's benchmark report.
4. `tune/train.py` trains a LoRA (rank 8 on the attention projections) on Gemma 2B, the base Workers AI serves for LoRA adapters, and compares it with the base model on the held-out examples. It writes the adapter with `model_type: gemma`, which Workers AI requires.
5. In production the adapter is uploaded with `npx wrangler ai finetune create @cf/google/gemma-2b-it-lora chef-reviewer <adapter dir>` and turned on with the `REVIEWER_LORA` var. `WorkersAiReviewer` then reviews with `env.AI.run(model, { prompt, raw: true, lora })` and leaves picking between parallel attempts to the Claude reviewer.

## Template

Projects Chef builds are React apps on Cloudflare Workers, made of Dune-style vertical slices:

```
features/<id>/index.ts       the feature's JSON routes under /api
features/<id>/pages.tsx      the feature's React pages
features/<id>/look.ts        optional part of the app's design system: brand, fonts, colors, scheme, radius, accent, width and CSS
features/<id>/<id>.test.ts   node:test tests, one per acceptance criterion
features/<id>/flow.ts        the user flow the proof drives
shared/                      http, storage, flow and paths contracts; the React app, router and UI kit
src/registry.gen.ts          generated from features/
src/index.ts                 the Worker entry
spec/features/<id>.md        the feature's spec
```

The Worker answers the features' routes and keeps data in one `StoreObject` Durable Object. Every other page address a browser opens gets the same small HTML shell (`shell` in `template/shared/http.ts`), which loads `/client.js`: `app build` (`template/app/client.ts`) bundles it with esbuild from every `features/<id>/pages.tsx` and `look.ts` (also one level down, in a role's folder) into `dist/client/`, which Workers serve as static assets without running the Worker. `wrangler.jsonc` runs that build before `wrangler dev` and `wrangler deploy`, so nothing generated is committed. In the browser, `shared/app.tsx` matches the address against the pages (a fixed segment before a parameter), shows a top bar with the brand and the `nav` pages, and moves between pages with `history.pushState`, so following a link never reloads the app; plain `<a>` links to the app's own pages work the same way. `/` opens the page whose path is `/`, or else the first `nav` page; an app with no pages yet says so, and an address no page answers says the page isn't built yet. API clients opening `/` get `{ ok: true }`, so a branch's app answers from the first commit; unknown API paths get `{ error: "not found" }`. A route that throws answers 500 with `{ error }`; the kit's `api()` and `message()` (`template/shared/ui.tsx`) turn any failed request into a message that is never empty. A page is a GET path with no params, outside `/api`, whose last segment has no file extension. Two routes with the same method and path (parameter names aside) cannot both be in the app: `createApp` refuses to build it and `app gen --check`, part of every gate, names the features that clash, so a later feature can never quietly take an earlier one's route. A route with a fixed segment wins over a parameter in the same place (`/api/books/top` before `/api/books/:id`), whichever feature registers first. The look is the app's design system: every feature's `look.ts` merges into one, which picks fonts from the catalog in `template/shared/fonts.ts` (the sandbox image installs them; `app build` copies the chosen files into `dist/client/fonts/` and writes `fonts.css`, which every page links, so fonts load from the app's own address), color tokens for light and dark or a single `scheme`, and a corner radius. `app look` (`template/app/look.ts`) opens pages in headless Chromium on a phone and a desktop, light and dark, and fails on text covered by another element or cut off by its box, contrast below 3:1, a page that scrolls sideways, and a chosen font that did not load; the gate runs it as the `look` check on the changed features' pages, and agents run it themselves before handing in. When the app is framed, its client posts the open path, its title and the app's pages to the frame's parent after every move (`report` in `template/shared/app.tsx`). The dashboard's App tab uses that for its address bar and its back and forward buttons; the app's own links do the rest, as in any browser. The App tab asks Chef whether the app runs only when it first opens or on Reload after a failure: once the app has loaded, moving to another page loads that page straight from the app's address in the same frame. The tab also opens the page named in the feature's entrypoint (`GET /notes`): a merged build opens it at once, while a build still in progress opens `/` and moves on to it as soon as the app lists it among its pages, saying until then that the page isn't built yet.

Feature tests make their app inside each test with `testApp(t, features)` (`template/app/testing.ts`), so every test starts from its own empty store and no test depends on what another left behind. `app.open(path)` serves the shell, the routes and a fresh esbuild bundle of the pages from memory to headless Chromium, so page tests need no build step and no network.

Code rules (`core/src/checks/code-rules.ts`) parse the TypeScript AST: no comments except tool directives; a feature may not import another feature; `shared/` may not import features; the app shell imports only `features/<id>/index.ts`; in projects with `app/testing.ts`, a feature's tests may not make a `MemoryStore` outside a test, where every test after it would share it.

## Project structure

A project either follows Chef's template or has its own structure, like a repository someone linked or imported. Chef places no limits on a project's stack and follows the repository's own structure, language, test tool and conventions. `usesChefTemplate` (`core/src/structure/structure.ts`) decides it from the tree of each commit, with no stored flag: a tree with the template's `app/gen.ts` and `src/registry.gen.ts` follows the template. Everything that only makes sense in the template depends on it:

| | Chef template | Own structure |
| --- | --- | --- |
| Generated files | `src/registry.gen.ts` regenerated into every commit and merge (`Orchestrator.regenerate`) | none; Chef never writes the registry |
| Checks (`SandboxCheckRunner`) | `tsc`, node tests of `features/`, `shared/` and `app/`, `app gen --check`, the template lint, with the template's `node_modules` | `repoChecks`: install the dependencies with the tool its lockfile or `packageManager` names (kept per lockfile in the sandbox between runs), then its package.json `typecheck`, `lint` and `test` scripts when they exist; a placeholder test script counts as none, and a repository without package.json reports that it has no checks instead of failing |
| Coder sandbox | the template's `node_modules` and the template lint after each turn (`runner.mjs`) | neither; the coder installs what it needs |
| Write scopes | the profiles' scopes as written | `ownScope`: the repository's real files and test files instead of `features/<id>/**` (see `agents/README.md`) |
| Red check, lanes, cross tests | new tests must fail against an empty stub of the feature, lanes start with one part file per role, attempts are scored on the tests under `features/<id>/` | no red check and no part files; attempts run the whole test suite |
| Proof | `app proof` drives `flow.ts` against the running app | `ProofRunner.probe` asks the running app for the feature's GET entrypoint (below 400) or `/` (below 500); a branch with no wrangler config or compose file has nothing to prove and passes with that said |
| Feature map | `feature-map` check and gardener spec entries for `features/<id>/` folders | neither |

Every prompt that builds or judges code, the planner's, every coder role's (test role included) and the reviewer's, ends with a short block from `structureGuidance` that says which kind the project is. For a project with its own structure it says to follow the repository's layout, language and test tool, to wire new code into the real app, never to create `features/`, `flow.ts`, `shared/ui.ts` or `src/registry.gen.ts`, and that a change is never rejected for missing template files or tests not named after criterion ids. Both kinds then get `COMPOSE_GUIDANCE` (`core/src/app/compose.ts`): how Chef runs a branch's stack from the root compose file and what any change to it must keep working. The planner and reviewer also get `ownStructure`, which drops template wording from the planner's prompt and has the Workers AI reviewer, tuned on template features, hand such reviews to the Claude reviewer. The test item asks for tests in the repository's own test tool instead of tests and `flow.ts`.

## HTTP API

Served by the Chef Worker (`workers/src/index.ts`):

| Method and path | Effect |
| --- | --- |
| `GET /api/keys` | The API keys: name, `chef_<id>_` prefix, kind (`key` or `controller`), scopes, whether it comes from the deployment's `CHEF_API_KEY`, when it was made, last used and ends; never the key itself |
| `POST /api/keys` | Makes a key from `{ name, kind?, expiresInDays? }` and returns it once as `token`; an ordinary key cannot make a controller key |
| `DELETE /api/keys/:id` | Revokes a key at once; the deployment's key is replaced by deploying again |
| `GET /api/projects/:name/shares` | The project's share links: what each opens (`session` or `app` and its id), its name, when it was made, last opened and ends; never the link's key |
| `POST /api/projects/:name/shares` | Makes a share link from `{ kind, id, expiresInDays? }` (30 days unless given; `null` for no end) and returns its key once as `token`; the dashboard turns it into `<origin>/s#<token>` |
| `DELETE /api/projects/:name` | Deletes the project and everything Chef made for it on Cloudflare (see "Deleting a project"); needs `{ confirm: name }` and returns what was removed and what was left as it is |
| `DELETE /api/shares/:id` | Ends a share link at once |
| `GET /api/share` | Called with a share link's key: what the link opens |
| `POST /api/projects/:name/app-key` | Gives the project's running apps a new key, so every open app and every link into one has to be opened again |
| `GET /api/settings` | The settings in use (Claude and voice providers, Cloudflare account, TypeSafe key, models, attempts, password source), with only the last four characters of each key and whether each comes from the dashboard or the deployment |
| `PUT /api/settings` | Saves any of `llm` (`{ kind: "anthropic", apiKey }` or `{ kind: "custom", baseUrl, apiKey }`), `voice` (`{ kind: "openai", apiKey }` or `{ kind: "custom", baseUrl, apiKey }`), `cloudflare` (`{ accountId, apiToken }`), `jev` (`{ apiKey }`), `models` (`{ planner, reviewer, coder }`) and `attempts`; `null` falls back to the deployment. `{ password }` alone changes the password and returns a new session cookie. Answers 409 for `llm`, `voice` and `jev` while a managing app manages them |
| `PUT /api/settings/managed` | Controller keys only. `{ by, llm, voice, jev }`: the providers the engine uses, each `null` or a provider with its base URL and key (`voice` may be `{ kind: "openai", apiKey, baseUrl }` for GPT Live through another address, `jev` `{ apiKey, baseUrl }`). `by` names the managing app in Settings. `DELETE` hands the providers back to the engine's own settings |
| `GET /api/projects/:name/settings` | The project's own settings: `appIdleMinutes`, and `git`, the linked repository (`url`, `branch`, `mode`, `syncBranch`, `webhookSecret`, the token's last four characters) or `null` |
| `GET`/`PUT /api/env` | Environment values every project gets; same body as a project's `env` |
| `GET`/`PUT /api/instructions` | Instructions shared by every project, with a `previous` check against overwriting a newer save |
| `GET`/`PUT /api/projects/:name/instructions` | The project's goal (`GOAL.md`) and instructions (`AGENTS.md`), committed to `main` |
| `GET`/`POST`/`PUT /api/projects/:name/memory` | Lists the project's memory documents, adds a note, or edits or removes one |
| `GET /api/projects/:name/feature-map` | The feature map on `main`: how to start the project and every feature with its parent, title, state and path |
| `POST /api/projects/:name/feature-map` | Changes the map with one commit on `main`: `{ kind: "add", parent, title, state?, path?, specs? }` (a wish unless `state` says otherwise), `{ kind: "update", id, … }`, `{ kind: "move", id, parent }`, `{ kind: "remove", id }` or `{ kind: "start", path }` |
